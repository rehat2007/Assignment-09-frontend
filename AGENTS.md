# Fix Mate frontend

FixMate marketplace app (Next.js 16 App Router, React 19.3, TypeScript, Tailwind CSS v4, shadcn `base-nova`) with Better Auth 1.7 + MongoDB. The Express API lives in the sibling folder `C:\web_dev\fix_mate\fix_mate_back_end`. Public pages are `/`, `/services`, `/services/[id]`, `/how-it-works`, `/sign-in`, `/sign-up`; authenticated pages are `/dashboard` plus the customer/technician/admin workspaces and `/dashboard/profile`. Auth runs on Express under `/api/auth`; avatar uploads go to Express, while `/api/avatar/[file]` only serves legacy local files. There is no test suite or CI. Accounts, the public catalog, customer bookings, technician listings/requests, admin actions, and Stripe payments live in MongoDB and are read through Express via `src/lib/api.ts` + the customer/technician/admin/catalog fetchers. Stripe checkout and webhooks are implemented; live payments require `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`.

- `src/app/page.tsx` composes the homepage sections in this order: hero, category strip, latest services, how it works, trust band, popular categories, why FixMate, testimonials, CTA, then the footer outside `<main>`. It is an async server component that fetches `/api/v1/meta` and the six newest `/api/v1/services` records, then passes them to the home sections. `layout.tsx` adds the navbar, Google fonts (Plus Jakarta headings, Inter body), and a pre-paint theme script.
- `/services` is a server component whose filters live entirely in the URL (`q`, `category`, `mode`, `sort`, `page`); category/mode chips and pagination are links, and the search/sort controls are a plain GET form. It fetches `/api/v1/meta` for categories/counts and `/api/v1/services` for the page. Keep it that way rather than adding client filter state.
- `/services/[id]` is the full service detail page: category hero, included items, service details, technician profile, review breakdown, and a booking card with role-aware CTA states. It reads `/api/v1/services/:slug` and `/api/v1/services/:slug/reviews`; unknown/publicly hidden slugs 404. It must not import the static `SERVICES` or `SERVICE_DETAILS`. Signed-in customers get `booking-request-dialog.tsx`, which posts only `serviceSlug`, `preferredDate`, `phone`, `address`, and `problem`; never send price, technician, status, or payment fields. `View details` links come from the shared card, so new listing links should use `/services/<id>`.
- `/how-it-works` is the About/pipeline page: hero job tracker, principles band, five-stage pipeline, values, native `<details>` FAQ, and a closing CTA. Its content is local to `src/app/how-it-works/page.tsx`; the navbar and footer both link there.
- `/sign-in` and `/sign-up` use `src/components/auth/auth-shell.tsx`; the navbar hides itself on those routes. Both forms call `authClient` and redirect to `/dashboard`; sign-in has `rememberMe`, and sign-up sends `accountType` (`customer` or `technician`).
- Sign-up has an optional profile-photo picker. The file is uploaded to `${NEXT_PUBLIC_API_URL}/api/v1/uploads/avatar` after the account is created (the route requires the new session), then its URL is saved with `authClient.updateUser({ image })`. New files land in `fix_mate_back_end/data/avatars`; the legacy `src/app/api/avatar/[file]` route only serves old files from the frontend `data/avatars` folder.
- Auth is Better Auth 1.7 + MongoDB in `fix_mate_back_end` (`src/auth.ts`, `src/db/mongo.ts`, `src/config/env.ts`). The frontend never imports the server auth module: `src/lib/auth-client.ts` points at `NEXT_PUBLIC_API_URL` with `credentials: "include"`, and `src/lib/authz.ts` fetches `${API_URL}/api/auth/get-session` with the forwarded browser cookie. Frontend `.env` needs `API_URL` and `NEXT_PUBLIC_API_URL` (plus optional Google vars for button visibility); backend `.env` owns `MONGODB_URI`, `MONGODB_DB`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (the backend origin), `FRONTEND_URL`, `GOOGLE_*`, `ADMIN_*`, and optional `MONGODB_DNS_SERVERS`. Restart `next dev` after changing `API_URL` or `NEXT_PUBLIC_API_URL`. The backend `trustedOrigins` and CORS must match the Next origin; `BETTER_AUTH_URL` is what cookies and OAuth callbacks use.
- Express `/api/v1` JSON uses `{ data, meta }` on success and `{ error: { code, message, details } }` on failure. `ApiError` plus the centralized `errorHandler` own status codes; `requestContext` echoes `X-Request-Id` and writes JSON access logs. Zod schemas live in `fix_mate_back_end/src/validation`; `validateBody`/`validateQuery`/`validateParams` populate `request.body`/`validatedQuery`/`validatedParams`. Pagination defaults are 9 (public), 20 (dashboard), max 100. `GET /api/v1/me` is read-only; profile mutations stay on Better Auth `POST /api/auth/update-user`. Avatar upload returns `{ data: { url } }`.
- `accountType` is a Better Auth additional user field and is sanitized in `databaseHooks.user.create.before` to `customer` or `technician`. Admin access uses the admin plugin's `role`, which public sign-up cannot set. Bootstrap the first admin with `npm run auth:admin` inside `fix_mate_back_end` after setting `ADMIN_EMAIL` and `ADMIN_PASSWORD` in the backend `.env`.
- `/dashboard/*` is protected server-side by `src/lib/authz.ts` (`getSession`, `requireUser`, `requireRole`). There is intentionally no proxy/middleware authorization layer; each role page calls `requireRole`, which redirects unauthenticated users to `/sign-in` and unauthorized roles to `/dashboard`. `/dashboard` itself redirects to `/dashboard/<role>`. Keep authorization checks in server components/route handlers, never only in the client. `getSession` is wrapped in React `cache`, so repeated calls within one request are cheap.
- `src/lib/roles.ts` owns frontend role resolution (the backend has the same helper in `fix_mate_back_end/src/roles.ts`). `getAppRole` returns `admin` if the admin plugin's `role` list (comma-separated) contains `admin`, else `technician` when `accountType === "technician"`, else `customer`. Use `getAppRole`, not raw `user.role`, for UI and redirects; `requireRole` uses it too.
- The dashboard layout (`src/app/dashboard/layout.tsx`) renders `DashboardShell`, which provides the role-specific sidebar, top bar, profile menu and mobile drawer. The public `SiteNavbar` hides itself on `/dashboard/*`. The catch-all `src/app/dashboard/[...section]/page.tsx` applies the matching role guard and returns 404 for unknown sections; add a static page under that path when implementing a new section. The layout fetches real sidebar counts (`pendingRequests`, `pendingServices`, `availableServices`) and passes them to `DashboardShell`; do not re-import preview arrays there.
- The navbar profile dropdown lives in `src/components/profile-menu.tsx`; it closes on outside click and Escape. `/dashboard/profile` updates `name`, `phone`, `area`, `bio` and `image` via `authClient.updateUser`; email, role and `accountType` are read-only by design.
- The customer workspace has `overview`, `bookings`, and `payments` under `src/app/dashboard/customer/`, plus the shared `/dashboard/profile` (`src/app/dashboard/profile/`) used by every role. All three read the API through `src/lib/customer-api.ts` with `withCookies: true`/`no-store`; the bookings page passes the first render to `CustomerBookings`, whose cancel button calls `POST /api/v1/bookings/:id/cancel` and whose Pay now button calls `POST /api/v1/bookings/:id/checkout`, then redirects to the returned Stripe Checkout URL. Customer payments show verified Stripe records. `src/lib/customer-data.ts` still holds the shared types/labels/formatters and the preview arrays used by other preview screens.
- The four technician pages (`overview`, `add-service`, `my-services`, `requests`) live under `src/app/dashboard/technician/` and read the API through `src/lib/technician-api.ts`. Listings support create, edit (approved/rejected edits return to `pending`), availability toggle, and soft delete. Requests support accept/reject/start/complete with a final-amount modal; requested bookings hide customer phone/address until accepted. Cover upload remains preview-only until Phase 8. The sidebar counts in `dashboard-shell.tsx` still use preview arrays until Phase 6.
- The five admin pages (`overview`, `users`, `services`, `bookings`, `transactions`) live under `src/app/dashboard/admin/` and read the API through `src/lib/admin-api.ts`. Users support role changes (customer ↔ technician), suspend/restore through Better Auth's ban mechanism, and self-demotion is blocked. Services can be approved/rejected only while `pending`; rejection stores a reason. The admin page, user table, approval queue, bookings, and payments all use live data; `src/lib/admin-data.ts` remains a seed/preview reference and is still used by the profile stats. Admin payments/revenue reflect verified Stripe payments.
- Google buttons render only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are both set in the frontend `.env` (used only to toggle the button). The real OAuth flow runs on Express; the Google Console redirect URI must be `http://localhost:4000/api/auth/callback/google` in dev (or `BETTER_AUTH_URL` + `/api/auth/callback/google` in production). Google sign-up creates a customer account; admin roles come only from the seed/admin tooling.
- Client components are `site-navbar.tsx`, `profile-menu.tsx`, `home-motion.tsx`, `theme-toggle.tsx`, the auth forms, `dashboard/profile-form.tsx`, `dashboard/dashboard-shell.tsx`, `customer/booking-request-dialog.tsx`, `technician/edit-service-dialog.tsx`, and the customer/technician/admin dashboard panels (including export, cancel, edit, request actions, and approval controls); everything else renders on the server. Keep new sections server-side unless they need state/effects.
- The visual reference is the standalone demo at `C:\web_dev\assignment_09-demo` (vanilla-JS hash-router SPA: `src/public.js`, `src/styles.css`, `src/data.js`). Use it to compare copy, spacing, and colors.
- Footer/legal links (`/privacy`, `/terms`, `/support`) and `/forgot-password` are scaffold placeholders pointing at routes that don't exist. Don't treat those 404s as regressions unless asked to build the pages.

## Commands

- `npm run dev` — Turbopack dev server. Starting a second instance fails and prints the existing server's PID, port, and log path; reuse it or stop it with `taskkill /PID <pid> /F`. Don't assume port 3000.
- `npm run build` — production build; Turbopack is the default bundler and the build also runs TypeScript checking.
- `npm run lint` — ESLint flat config (`eslint.config.mjs`) with `eslint-config-next` core-web-vitals and TypeScript rules. Next 16 has no `next lint` command.
- `npx tsc --noEmit` — standalone typecheck (there is no `typecheck` script). `tsconfig.tsbuildinfo` is a local artifact.
- After adding/moving routes (or when `.next/types` is missing), run `npx next typegen` before `npx tsc --noEmit`; it also regenerates `next-env.d.ts`.
- `npm run auth:admin` — run inside `fix_mate_back_end`, not the frontend. Creates or promotes an admin. Requires `ADMIN_PASSWORD` (≥8 chars) in the backend `.env`; `ADMIN_EMAIL` defaults to `admin@fixmate.dev`; `ADMIN_NAME` is optional.
- `npm run seed` — run inside `fix_mate_back_end`. Ensures marketplace indexes and upserts the 15 services, 3 technician profiles, demo users, and seed reviews. It is idempotent; existing users keep their passwords. Non-admin demo accounts use `SEED_PASSWORD`.
- Use npm (`package-lock.json` is the only lockfile). No tests are configured — don't invent a test command or add a runner unless asked.

## Data, cards, and animation hooks

- `src/lib/services.ts` remains the type/seed source for the 15 demo listings (`Service`, `CATEGORIES`, `PAGE_SIZE = 9`, `newestServices`). Its data is mirrored into the backend seed fixture (`fix_mate_back_end/scripts/seed-data.ts`) and seeded into MongoDB. The public pages read the API through `src/lib/catalog.ts`; do not import the `SERVICES`/`CATEGORIES` arrays into pages again. `src/lib/service-details.ts` is seed-only now: `SERVICE_DETAILS`, `TECHNICIANS`, and `getServiceDetail` feed the seed fixture, while the detail page uses the API's `includes`, `warranty`, `availabilityNote`, and `technicianProfile`.
- `src/lib/api.ts` is the server-only fetch wrapper: it reads `API_URL`, unwraps `{ data, meta }`, throws `ApiRequestError`, and forwards cookies only when asked. Public catalog fetches use the `catalog` cache tag; `src/app/actions.ts` calls `updateTag("catalog")` after listing mutations so edits/deletes/pauses/approvals show up immediately. `src/lib/catalog.ts`, `src/lib/customer-api.ts`, `src/lib/technician-api.ts`, and `src/lib/admin-api.ts` own the authenticated fetchers. Admin role/suspend/approve/reject actions are written to the backend `auditLogs` collection; the read endpoint is P2.
- Stripe lives in `fix_mate_back_end/src/lib/stripe.ts`. `POST /api/v1/bookings/:id/checkout` requires the owning customer, a `completed` + `unpaid` booking, and a positive server-side `finalAmount`; it creates a Checkout Session and stores `checkoutSessionId` on the booking. `POST /api/v1/webhooks/stripe` is mounted with `express.raw()` before `express.json()`, verifies the signature with `STRIPE_WEBHOOK_SECRET`, and handles `checkout.session.completed` + `payment_intent.succeeded`. Payments are inserted idempotently by `bookingId` (unique) and the booking is marked paid only after the verified webhook. The customer Pay now button redirects to the returned Checkout URL. For local testing, fill the two Stripe env keys and run `stripe listen --forward-to localhost:4000/api/v1/webhooks/stripe`.
- `popular-categories.tsx` receives category counts and service/technician totals from `/api/v1/meta`; `/services` uses the same meta counts. Do not reintroduce hardcoded totals.
- `src/lib/home-data.ts` holds home-only copy (steps, stats, why-FixMate, testimonials). Catalog-derived featured services and category counts come from the API in `src/app/page.tsx`.
- `src/components/service-card.tsx` is shared by the homepage and `/services`. Change the card once there; it links each listing to `/services/<id>`.
- `src/lib/service-styles.ts` supplies the category icon/tone maps used by the strip, cards, and category tiles.
- `src/components/home-motion.tsx` is the only animation code: GSAP + ScrollTrigger with a `prefers-reduced-motion` guard. It targets `data-hero`, `data-hero-art`, `data-reveal`, `data-reveal-group`, `data-float` (7s vertical float; `data-float-delay` sets the phase offset), and `data-scan` (scan line in the hero card). Add those attributes instead of writing per-section animation code, and mount `<HomeMotion />` on any page that uses them (already on the homepage, `/services`, `/services/[id]`, and `/how-it-works`).
- `popular-strip.tsx` is an unused earlier draft; the live strip is `category-strip.tsx`.
- Homepage sections use `.site-container` (max-width 1264px, 1216px of content after 14/16/24px gutters at the 561/761px breakpoints). `/services`, `/services/[id]`, and `/how-it-works` use `mx-auto max-w-[1264px] px-6` instead (the detail page also uses `.site-container`). Dashboard pages keep `max-w-[1264px] px-6`. Navbar links are `/`, `/services`, `/how-it-works`; the navbar is 74px tall on desktop and 64px at ≤760px (`scroll-mt-[74px]`).
- Public home sections follow the demo rhythm: standard sections use `py-[clamp(52px,6.5vw,92px)]`, tight sections use `py-[clamp(38px,4.5vw,60px)]`, and responsive grids switch at the demo's 381/561/761/861/981/1101px breakpoints. `PopularCategories` renders the Why FixMate block inline rather than as a separate section.

## Conventions that differ from framework defaults

- Import the class-name helper as `import { cn } from "cn"`. It comes from the `cn` package; do not add `clsx`/`tailwind-merge`, and don't assume `@/lib/utils` is the source (`src/lib/utils.ts` only re-exports `cn`).
- UI primitives are Base UI (`@base-ui/react/...`), not Radix. Match the existing patterns in `src/components/ui/` and keep new shadcn components there; aliases are defined in `components.json`.
- Tailwind v4 is CSS-first: there is no `tailwind.config.*`. Theme tokens and dark mode live in `src/app/globals.css` (`@theme inline`, oklch variables, `@custom-variant dark (&:is(.dark *))`). CSS is compiled by the `@tailwindcss/turbopack` loader rule in `next.config.ts`, not by PostCSS — do not add a PostCSS config for it.
- Landing sections use hardcoded hex/arbitrary-value colors with explicit `dark:` classes, not the shadcn tokens. Changing `globals.css` variables restyles `src/components/ui/` primitives but not the page sections.
- The theme toggle (`SiteNavbar`) adds/removes `.dark` on `<html>` and persists to `localStorage` under `fixmate-theme`; `layout.tsx` replays that before paint to avoid a flash. Keep the key and the `suppressHydrationWarning` on `<html>` in sync.
- Use the `@/*` alias for `src/*`.
- `PageProps<"/route">`, `LayoutProps<"/">`, and `RouteContext` are generated global types (`npx next typegen` writes `.next/types`; `next dev` uses `.next/dev/types`); use them without importing. Never hand-edit `next-env.d.ts` (generated, gitignored).
